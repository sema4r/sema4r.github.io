Tile-based frameworks like [NVIDIA CuTe/CUTLASS](https://github.com/NVIDIA/cutlass) and [ThunderKittens](https://github.com/HazyResearch/ThunderKittens) 
from Stanford's Hazy Research Lab produce already highly-optimized PTX/SASS code.
Building on these frameworks, mid-level libraries like [cuBLAS/cuBLASLt](https://developer.nvidia.com/cublas), [cuDNN](https://developer.nvidia.com/cuda/cuda-x-libraries/cudnn)
and [FlashAttention3](https://github.com/Dao-AILab/flash-attention) provide ML-specific operations like (standard) GEMMs, convolution and attention variants, 
even with additional hand-tuned PTX/SASS kernels.

While this tool set is fully sufficient for most use cases, highly customized high performance kernels often do need more fine-grained control over 
data movement, register-level operations, memory ordering and synchronization semantics. The next posts of this series will look into such low-level optimization 
techniques i.e. will be exploring the field of micro-architectural tuning. 

Instruction scheduling, asynchronous barrier synchronization and cache eviction policies are some of the topics we will cover. As will be persistent kernels, 
warp-specialized pipelines and distributed shared memory (DSM) transfers.  

As we will see, this does in many cases involve inline PTX/SASS code. This is no coincidence. Hardware ISAs usually evolve faster than higher level APIs, so not
every architecture-specific hardware instruction is available from early on. Other, specialized PTX primitives are by design not intended to be exposed in CUDA 
C++ at all. Finally, even for explicit CUDA C++ code, the compiler infrastructure (NVVM/cicc + ptxas) does not guarantee the supposed PTX or SASS output. Not even 
for something as simple as a vectorized store/load. (See the code snippets below with the CUDA C++ code and the expected PTX and SASS primitives.)
Potential obstructions for the emission of optimized instructions at compile step C++ CUDA -> PTX code  (NVVM/cicc) are alignment knowledge, aliasing information,
access pattern identification and internal optimization heuristics. A too low optimization level (< O3) can stop optimization all together. At compile step 
PTX -> SASS (ptxas), instruction selection, register pressure, register spilling and instruction scheduling affect the generation of optimized code.
Lesson : CUDA C++ expresses intent, but the compiler toolchain chooses the final instructions. Profiling the generated PTX and SASS code therefore is essential.

__global__ void kernel(float4* output) {

	__shared__ __align__(16) float smem[1024];

  	int idx = threadIdx.x * 4;

  	smem[idx + 0] = 1.0f;
  	smem[idx + 1] = 2.0f;
  	smem[idx + 2] = 3.0f;
  	smem[idx + 3] = 4.0f;

  	_syncthreads();

  	const float4* __restrict__ __align__(16) ptr
    	                        = reinterpret_cast<const float4*>(&smem[idx]);

  	output[threadIdx.x] = ptr[0];

}

```cpp
__global__ void kernel(float4* output) {

  	__shared__ __align__(16) float smem[1024];

	const unsigned int tid = threadIdx.x;
  	const unsigned int idx = tid * 4;

  	smem[idx + 0] = 1.0f;
  	smem[idx + 1] = 2.0f;
	smem[idx + 2] = 3.0f;
  	smem[idx + 3] = 4.0f;

  	_syncthreads();

	// output registers
  	float x, y, z, w;

  	asm volatile(
		"ld.shared.v4.f32 {%0, %1, %2, %3}, [%4];"
      	: "=r"(x), "=r"(y), "=r"(z), "=r"(w)
      	: "r"(&smem[idx])
      	: "memory"
  	);

	asm volatile(
		"st.global.v4.f32 [%0], {%1, %2, %3, %4};"
		:
		: "l"(&output[tid]),
      	  "f"(x), "f"(y), "f"(z), "f"(w)
      	: "memory"
    );

}
```
