Tile-based frameworks like NVIDIA CuTe/CUTLASS and ThunderKittens from Stanford's Hazy Research Lab produce already highly-optimized PTX/SASS code.<br>
Building on these frameworks, mid-level libraries like cuBLAS, cuDNN and FlashAttention3/4 provide ML-specific operations like (standard) GEMMs, convolution 
and attention variants, even with additional hand-tuned PTX/SASS kernels.

While this tool set is fully sufficient for most use cases, highly customized high performance kernels often do need more fine-grained control over 
compute and memory pipelines. The next posts of this series will look into such low-level optimization techniques aka micro-architectural tuning. 

Instruction scheduling, asynchronous barrier synchronization and cache eviction policies will be some of the topics we will cover. Persistent kernels, 
warp-specialized pipelines and distributed shared memory (DSM) transfers are on my list too.  

As we will see, this does in many cases involve inline PTX/SASS code. That's no coincidence. Many exact PTX primitives are not cleanly exposed in CUDA C++. 
Furthermore, even with explicit C++ code for something as simple as a vectorized store/load, the CUDA compiler infrastructure (NVVM/cicc + ptxas) does not 
guarantee a vectorized PTX or SASS output. (See the code snippets below with the C++ code and the expected PTX and SASS primitives.)

__global__ void kernel(float4* output) {

  __shared__ __align__(16) float smem[1024];

  int idx = threadIdx.x * 4;

  smem[idx + 0] = 1.0f;
  smem[idx + 1] = 2.0f;
  smem[idx + 2] = 3.0f;
  smem[idx + 3] = 4.0f;

  const float4* __restrict__ __align__(16) ptr
                            = reinterpret_cast<const float4*>(&smem[idx]);

  output[threadId.x] = ptr[0];

}

Potential obstructions for the emission of optimized instructions, by compile step :

<br>
C++ CUDA $\; \longrightarrow \;$ PTX code  (NVVM/cicc) 

- Alignment knowledge.

- Aliasing information.

- Access pattern identification.
  
- Optimization level too low.

- Optimization heuristics 

<br>
PTX $\; \longrightarrow \;$ SASS (ptxas)

- Instruction selection.
  
- Register pressure too high. Based on its internal bookkeeping and heuristics, the compiler conducts a static analysis about the 
    expected usage of registers. If the compiler is low, on registers it might emit scalar loads for a more flexible schedule. 
- Register spilling

- Instruction scheduling.

- Architecture-specific lowering

<br>
Lesson here : CUDA C++ expresses intent, but the compiler toolchain chooses the final instructions.
