Tile-based frameworks like NVIDIA [CuTe/CUTLASS](https://github.com/NVIDIA/cutlass) and [ThunderKittens](https://github.com/HazyResearch/ThunderKittens) 
from Stanford's Hazy Research Lab produce already highly-optimized PTX/SASS code.
Building on these frameworks, mid-level libraries like [cuBLAS](https://developer.nvidia.com/cublas), [cuDNN](https://developer.nvidia.com/cuda/cuda-x-libraries/cudnn)
and [FlashAttention3](https://github.com/Dao-AILab/flash-attention) provide ML-specific operations like (standard) GEMMs, convolution and attention variants, 
even with additional hand-tuned PTX/SASS kernels.

While this tool set is fully sufficient for most use cases, highly customized high performance kernels often do need more fine-grained control over 
data movement, register-level operations, memory ordering and synchronization semantics. The next posts of this series will look into such low-level optimization 
techniques i.e. will be exploring the field of micro-architectural tuning. 

Instruction scheduling, asynchronous barrier synchronization and cache eviction policies are some of the topics we will cover. As will be persistent kernels, 
warp-specialized pipelines and distributed shared memory (DSM) transfers.  

As we will see, this does in many cases involve inline PTX/SASS code. That's no coincidence. Hardware ISAs usually evolve faster than higher level APIs, so not
every architecture-specific hardware instruction is available from early on. Other, specialized PTX primitives are by design not intended to be exposed in CUDA 
C++ at all. Finally, even for explicit CUDA C++ code, the compiler infrastructure (NVVM/cicc + ptxas) does not guarantee the supposed PTX or SASS 
output. (Not even for something as simple as a vectorized store/load. See the code snippets below with the CUDA C++ code and the expected PTX and SASS primitives.)

```cpp
__global__ void kernel(float4* output) {

  __shared__ __align__(16) float smem[1024];

  int idx = threadIdx.x * 4;

  smem[idx + 0] = 1.0f;
  smem[idx + 1] = 2.0f;
  smem[idx + 2] = 3.0f;
  smem[idx + 3] = 4.0f;

  const float4* __restrict__ __align__(16) ptr
                            = reinterpret_cast<const float4*>(&smem[idx]);

  output[threadId.x] = ptr[0];

}
```

Potential obstructions for the emission of optimized instructions, by compile step :
<br>
C++ CUDA $\; \longrightarrow \;$ PTX code  (NVVM/cicc) : 

- Alignment knowledge.
- Aliasing information.
- Access pattern identification.
- Optimization level too low.
- Optimization heuristics 
<br>
PTX $\; \longrightarrow \;$ SASS (ptxas)

- Instruction selection.
- Register pressure too high. Based on its internal bookkeeping and heuristics, the compiler conducts a static analysis about the 
    expected usage of registers. If the compiler is low, on registers it might emit scalar loads for a more flexible schedule. 
- Register spilling
- Instruction scheduling.
- Architecture-specific lowering

Lesson : CUDA C++ expresses intent, but the compiler toolchain chooses the final instructions. Profiling is essential. <br> 

The inline PTX code for the 128-bit load from above :

{% raw %}
```cpp
__shared__ __align__(16) int smem[4];
int* ptr = smem;

int x0, x1, x2, x3;

asm volatile(
    "ld.shared.v4.b32 {%0, %1, %2, %3}, [%4];\n"
    : "=r"(x0), "=r"(x1), "=r"(x2), "=r"(x3)
    : "r"(ptr) 
);
```
