Vectorized load is used all over the place in performance-critical transformer-based environments. But making the compiler (cicc + ptxas) 
actually generate the correct SASS code is tricky. Even the explicit code below for example does not guarantee that cicc will always emit 
'ld.shared.v4.b32' (or 'ld.global.v4.b32' for global memory) i.e. the PTX code for a vectorized 128-bit load. 

```cpp
__global__ void kernel(float4* output) {

  __shared__ __align__(16) float smem[1024];

  int idx = threadIdx.x * 4;

  smem[idx + 0] = 1.0f;
  smem[idx + 1] = 2.0f;
  smem[idx + 2] = 3.0f;
  smem[idx + 3] = 4.0f;

  const float4* __restrict__ __align__(16) ptr = reinterpret_cast<const float4*>(&smem[idx]);

  float4 x = ptr[0];

  output[idx + 0] = x.x;
  output[idx + 1] = x.y; 
  output[idx + 2] = x.z;
  output[idx + 3] = x.w;

}
```

Possible reasons are :

(1) Optimization level too low. Vectorization might not happen for levels < O3 .

(2) Register pressure too high. Based on its internal bookkeeping and heuristics, the compiler conducts a static analysis about the 
    expected usage of registers. If the compiler is low, on registers it might emit scalar loads for a more flexible schedule.

(3) Alignment knowledge

(4) Aliasing information 


Philosophy : CUDA C++ expresses intent, but ptxas chooses the final instructions. 

That's why performance-critical libraries like CUTLASS/cuBLASLt or TensorRT use inline PTX for vector loads.

Code looks like this :

{% raw %}
```cpp
__shared__ __align__(16) int smem[4];
int* ptr = smem;

int x0, x1, x2, x3;

asm volatile(
    "ld.shared.v4.b32 {%0, %1, %2, %3}, [%4];\n"
    : "=r"(x0), "=r"(x1), "=r"(x2), "=r"(x3)
    : "r"(ptr) 
);
```
